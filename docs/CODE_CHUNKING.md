# How repository code is chunked

This guide describes the current `repository_rag` implementation using the Quote API fixture.
It covers source code, including method bodies. These are **syntax-based code chunks**, not
summaries generated by an AI model.

## 1. Read and prepare files

The indexer reads supported repository files, records each original file's SHA-256 hash, and
redacts recognizable secrets before parsing or embedding. It skips build/vendor directories,
generated C# files, out-of-root links, and files outside its size limits. The redacted text keeps
line positions for source citations. Redaction is pattern-based, so review a repository before
allowing cloud embedding or semantic interpretation.

For `.cs` files, a syntax-only Roslyn parser identifies types, methods, constructors, properties,
fields, enum members, local functions, and top-level statements. It does not build or execute the
uploaded project for this chunking step. Other supported text files receive a file chunk and,
when needed, smaller windows; they do not receive a C# syntax hierarchy.

## 2. Build a parent-child hierarchy

For [`QuoteResponse.cs`](../fixtures/RegionalQuoteApi/src/RegionalQuoteApi/Models/QuoteResponse.cs):

```text
QuoteResponse.cs                          file, lines 1-26
├── QuoteResponse                         class, lines 3-12
│   ├── QuoteId                            property, line 5
│   ├── Status                             property, line 7
│   ├── Premium                            property, line 9
│   └── ValidUntil                         property, line 11
├── CoverageType                          enum, lines 14-19
│   ├── Liability                          enum member
│   ├── Collision                          enum member
│   └── Comprehensive                      enum member
└── QuoteStatus                           enum, lines 21-26
    ├── Draft                              enum member
    ├── Offered                            enum member
    └── Expired                            enum member
```

The `Premium` property has its own chunk whose code text is:

```csharp
public decimal Premium { get; init; }
```

It also has a `CONTAINS` edge from the `QuoteResponse` class chunk. Parent chunks include their
source span, so the class preview overlaps the property text by design: the child is precise
evidence, while the parent supplies nearby context.

## 3. Keep method instructions together

For [`InMemoryQuoteService.cs`](../fixtures/RegionalQuoteApi/src/RegionalQuoteApi/Services/InMemoryQuoteService.cs):

```text
InMemoryQuoteService.cs                   file
└── InMemoryQuoteService                  class
    ├── _quotes                           field
    ├── Create(CreateQuoteRequest request) method, lines 10-22
    └── Get(Guid quoteId)                 method, lines 24-25
```

The `Create` method chunk contains its signature **and body**, including the following source
instructions:

```csharp
var quote = new QuoteResponse
{
    Premium = decimal.Round(request.CoverageAmount * 0.0125m, 2),
    // Other QuoteResponse fields are set here.
};
_quotes[quote.QuoteId] = quote;
return quote;
```

The shortened block above is illustrative; the stored chunk contains the actual redacted source,
not this edited excerpt. Individual assignments, `if` statements, and return statements are **not**
separate syntax chunks. Keeping a method body together helps retrieval show the calculation,
storage, and return in their immediate context. Method overloads have distinct signatures and
source positions, so they are not merged merely because their names match. A local function
inside a method becomes a child chunk.

## 4. Split long bodies without losing the tail

Each file/type/member chunk stores at most 1,800 characters as its preview. If its source span is
longer, the indexer creates additional `window` child chunks, each at most 1,800 characters and
linked to the parent with `CONTAINS`. Windows follow source lines and record their own line ranges.
They cover the entire long span, including code beyond the parent's preview. This also covers
using directives and dependency-injection/top-level code outside named members via file windows.

## 5. Store identity and relationships

Each chunk records fields such as:

```json
{
  "kind": "PropertyDeclaration",
  "symbol": "RegionalQuoteApi.Models.QuoteResponse.Premium",
  "path": "src/RegionalQuoteApi/Models/QuoteResponse.cs",
  "startLine": 9,
  "endLine": 9,
  "parentId": "<class chunk ID>",
  "sha256": "<original file SHA-256>",
  "text": "    public decimal Premium { get; init; }"
}
```

The IDs and hash placeholders above are explanatory, not literal fixture values. Actual chunk
IDs are deterministic hashes derived from the source identity and syntax position. The saved
manifest also retains `CONTAINS` edges and name-based `CALLS_CANDIDATE`,
`REFERENCES_CANDIDATE`, and `INHERITS_CANDIDATE` edges. Those last three mean “possibly related,”
not “this runtime call or type binding is proven.” Missing or ambiguous references remain visible.

## 6. How retrieval uses the chunks

Each vector-store document contains the path, symbol, and chunk text. If Discovery has a precise
source binding—for example `QuoteResponse.Premium`—retrieval prioritizes that exact chunk. It
also ranks lexical and embedding matches, then adds bounded parent or related chunks. A question
such as “how is Premium calculated?” can retrieve the `Premium` property and the service method
containing the calculation. The API Analyzer may then explain the retrieved source with citations;
focused interpretation reports separate code claims that cite retrieved chunk IDs. A selected
target without a grounded code claim remains partial. An embedding score by itself is not a
business conclusion or proof of a call path.
